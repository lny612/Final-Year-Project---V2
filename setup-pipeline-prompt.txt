STEP 3: CREATE settings.json
================================================================================

Create `.claude/settings.json` with this EXACT content:

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "bash -c 'FILE=\"$TOOL_FILE_PATH\"; case \"$FILE\" in *.unity|*.prefab|*.asset|*.meta) echo \"BLOCKED: Do not modify Unity binary/meta files: $FILE\" >&2; exit 2;; esac; exit 0'"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "shell": "powershell",
            "command": "[Console]::Beep(1200, 300); [Console]::Beep(1500, 200)",
            "timeout": 5
          }
        ]
      }
    ],
    "Notification": [
      {
        "hooks": [
          {
            "type": "command",
            "shell": "powershell",
            "command": "[Console]::Beep(800, 400); [Console]::Beep(800, 400)",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

EXPLANATION OF EACH SECTION:
- `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`: Enables the agent team system (leader
  can spawn sub-agents with Agent tool). Without this, agent teams do NOT work.
- `PostToolUse` hook on `Write|Edit`: Intercepts every file write/edit and blocks
  it if the target is a Unity binary file (.unity, .prefab, .asset, .meta).
  This is a safety net — these files are binary/serialized YAML and Claude Code
  will corrupt them if it tries to edit them directly.
- `Stop` hook: Plays a two-tone beep (1200Hz then 1500Hz) when Claude Code stops
  working, so you get an audio notification that it's done.
- `Notification` hook: Plays a double beep (800Hz) for notification events
  (e.g., when a background agent completes).

NOTE: The beep commands use PowerShell syntax for Windows. On macOS, replace with:
  "command": "afplay /System/Library/Sounds/Glass.aiff"
On Linux, replace with:
  "command": "paplay /usr/share/sounds/freedesktop/stereo/complete.oga"

```markdown

paths:
  - "Assets/**/*"

# Unity File Safety Rules

## NEVER Create or Modify
- `.unity` scene files (binary/serialized YAML)
- `.prefab` prefab files
- `.asset` ScriptableObject/settings files
- `.meta` files (Unity auto-generates these when it detects new files)
- Anything under `Library/`, `Temp/`, `obj/`, `Logs/`

## When Inspector Wiring Is Needed
Add a `TODO-EDITOR:` comment with exact instructions:
```csharp
// TODO-EDITOR: Add [ComponentName] component to [PrefabName] prefab (Assets/Prefabs/[path])
// TODO-EDITOR: Assign [fieldName] field in Inspector (create URP/Lit material, [color] tint)
// TODO-EDITOR: Create new UI element under Canvas > [hierarchy path] (Image, anchored [position])
```

## New Script Files
- Place in `Assets/Scripts/` (flat structure, no subfolders — unless the project already uses subfolders)
- Unity generates the `.meta` file automatically on next Editor focus
- Do NOT create `.meta` files manually

## Scene Setup
- Document required scene changes in `TODO-EDITOR:` comments or design docs
- Include: GameObject name, component to add, field values, hierarchy position
```

EXPLANATION: The `paths:` frontmatter tells Claude Code this rule only activates
when working on files under Assets/. The rule prevents corruption of Unity binary
files and establishes the `TODO-EDITOR:` pattern for things that need manual
Inspector work.

STEP 5: ANALYZE PROJECT AND DEFINE PROGRAMMER DOMAINS
================================================================================

This is the most important customization step. Based on Step 1's analysis,
you must decide HOW MANY programmer agents to create and WHAT each one owns.

PRINCIPLES FOR DOMAIN SPLITTING:
- Each .cs file must belong to EXACTLY ONE programmer agent
- Group files by functional domain (not by file count)
- Minimize cross-domain dependencies — files that heavily reference each other
  should be in the same domain
- Typical splits for a Unity game:
  * "gameplay-programmer" — core gameplay mechanics, player actions
  * "systems-programmer" — infrastructure: managers, data flow, scene management
  * "ui-programmer" — all UI scripts, HUD, visual feedback
  * "ai-programmer" — AI/ML integration, NPC behavior (if applicable)
  * "network-programmer" — multiplayer/API calls (if applicable)
- Small projects (< 15 scripts) might only need 2 programmers
- Large projects (> 40 scripts) might need 3-4 programmers

For each programmer domain, list ALL files it owns. Leave no script unassigned.

================================================================================
HOW TO USE THE PIPELINE (reference for the user)
================================================================================

Once set up, the workflow is:

1. WRITE YOUR GDD: Fill in `Docs/GDD.md` with your game's mechanics, rules,
   and design vision. This is the source of truth the designer agent reads.

2. REQUEST A FEATURE: Tell Claude Code what you want. For complex features,
   it will automatically use the leader agent to orchestrate.

3. DESIGN PHASE: The designer writes a spec at `Docs/designs/<feature>.md`
   with file ownership and interface contracts.

4. IMPLEMENTATION PHASE: Programmer agents work in parallel on isolated
   worktree branches, each implementing their owned files.

5. MERGE: The leader merges branches in dependency order.

6. MANUAL WIRING: Search for `TODO-EDITOR:` comments and do the Inspector
   work in Unity Editor (assign references, create UI elements, etc.).

7. REVIEW: Use `/review-code Docs/designs/<feature>.md` to verify the
   implementation matches the spec.

You can also use individual skills directly:
- `/design-doc <feature>` — just write a design doc
- `/implement <design-doc-path>` — implement from an existing design doc
- `/implement-vfx <design-doc-path>` — implement VFX from a design doc
- `/review-code <design-doc-path>` — review implementation against spec
